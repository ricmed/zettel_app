## Summary

zettel_app is a Python 3.12 pipeline (harvest → extract → review → connect → garden) that converts PDF/Markdown source material into an Obsidian-compatible Zettelkasten vault, backed by a dual-store persistence model (SQLite for structured/relational state, ChromaDB for vector search) and a hybrid retrieval layer (dense + BM25 fusion with a relevance floor and graph expansion) that feeds a FastAPI web UI, a `zettel ask` Q&A command, and a `zettel article` long-form writing pipeline built on LangGraph. The codebase is organized as a set of largely single-responsibility modules under `zettel/`, orchestrated by one large Typer CLI (`cli.py`) that holds no business logic of its own — every command delegates to a pipeline or infrastructure module.

Two modules, `config.py` and `state.py`, sit at the structural center of the codebase: nearly every other module depends on one or both of them (25 and 22 dependents respectively per the architectural analysis), making them the highest-blast-radius surfaces for any breaking change. `cli.py` is the mirror image — the single module with the broadest reach outward (21 internal dependencies) and, notably, the only major module confirmed to have zero direct test coverage anywhere in the 391-test suite (no `CliRunner`, no subprocess test, no `conftest.py` to share fixtures across the 37 test files). The dual SQLite/ChromaDB persistence model has no cross-store transaction guarantee — a risk the project's own CLAUDE.md already flags as something requiring manual discipline — and this was independently rediscovered from different angles in the `review`, `index`, `state`, `purge_source`, and `sync` component reports.

Dependency health is generally solid for the actively-maintained web/data stack, but the audit surfaced three real risks worth tracking: an unpatched RCE CVE in `chromadb`'s (unused) network server component, the permanent end-of-life of `bleach` (the project's only HTML sanitizer), and an AGPL-3.0 licensing exposure from `PyMuPDF` that matters if the web UI is ever exposed beyond personal/local use. No dangerous patterns (`eval`, `exec`, `subprocess`, `pickle`, `shell=True`) were found anywhere in the codebase, and the web layer's security controls (HMAC-signed session cookies, CSRF, upload path-traversal guards, two-layer HTML sanitization) were assessed as solid — with one notable exception, an explicitly acknowledged and still-unmitigated prompt-injection risk documented in-code in `connector.py`.

## Architecture Overview

The pipeline runs in five phases, each backed by its own module: **Phase 1** (`harvester.py` + `paging.py`) ingests PDFs/Markdown, resolves pagination, chunks text, and runs three-layer duplicate detection (file hash → extraction hash → semantic similarity). **Phase 2** (`extractor.py`) turns chunks into draft literature notes via an LLM call, with deterministic response caching (`hashing.py`) and its own dedupe logic deliberately kept separate from the shared retrieval stack because its thresholds are calibrated on raw L2 distance. **Phase 2b** (`review.py`) is a human-in-the-loop approval gate that promotes drafts into the vault and embeds them into ChromaDB. **Phase 3** (`connector.py`) uses the hybrid `Retriever` (`retrieval.py`) for RAG context to generate permanent (Zettelkasten) notes, with typed bidirectional backlinks. **Phase 4** (`gardener.py`, `gardener_assign.py`) and **Phase 4b** (`gardener_hub.py`) build Maps of Content (MOCs) via two complementary strategies — taxonomy-driven clustering (UMAP+HDBSCAN, with a KMeans fallback silently triggered if those optional packages aren't installed) and hub-anchored graph-degree neighborhoods — both funneling through the shared `moc_backrefs.py` for backlink maintenance.

Cutting across the linear pipeline, `sync.py` indexes manually-created or hand-edited vault notes (`new_note.py` scaffolds them) and closes the graph loop by persisting `[[wikilinks]]` found in note bodies as typed graph edges, never downgrading an already-typed one. `purge_source.py` and the CLI's `purge-rejected` path provide the only irreversible deletion operations, both CLI-only and both carrying the same cross-store-consistency caveat as the rest of the persistence layer. The retrieval layer (`retrieval.py`, `graph.py`) fuses ChromaDB dense search with SQLite FTS5 BM25 via Reciprocal Rank Fusion, then applies a documented, previously-buggy-in-production relevance floor before optionally expanding surviving hits over the note graph via weighted BFS — this fused `Retriever` is the shared foundation for `ask.py` (which skips the LLM call entirely and returns a deterministic "no evidence" answer when nothing clears the floor), `article.py`/`article_graph.py` (a 13-node LangGraph long-form writing pipeline with HITL checkpoints, a bounded judge/redraft loop, and ABNT citation support via `bibliography.py`), `connector.py`, and `sync.py`'s suggestion engine. A FastAPI web UI (`web.py` + `web_app.py`, presented through 14 Jinja2 templates) wraps a curated subset of these operations behind a single-worker job queue with HMAC-authenticated sessions, though it exposes narrower gating on some operations (e.g. the manual review endpoint) than the CLI does for the equivalent flow.

Rounding out the codebase: `pricing.py`/`usage.py` provide LiteLLM-backed cost estimation and per-run/per-source aggregation with no local price table; `schemas.py` is a pure Pydantic v2 DTO layer for every LLM structured output; `chunk_dump.py`/`extraction_dump.py`/`rebuild.py` are opt-in diagnostic and recovery utilities; and `prompts/*.md` (17 files) encode the actual LLM contracts — each split into a stable system section and a per-call user payload via a `<!-- zettel:user -->` marker. Two root-level scripts, `main.py` and `cuda-test.py`, are confirmed vestigial dead code with zero references anywhere in the project.

## Dependencies Health

Three risks were rated critical by the dependency audit: an unauthenticated RCE (CVE-2026-45829, CVSS 10.0) in `chromadb==1.5.9`'s FastAPI server component — mitigated here because the codebase only ever instantiates ChromaDB's embedded `PersistentClient`, never the network server, but the vulnerable code path is still present in the installed package; `bleach==6.4.0` (the sole HTML sanitizer feeding the web UI, used in tandem with `markdown.py`'s own allow-list pass) reaching permanent end-of-life with no further patches ever coming; and `PyMuPDF` being AGPL-3.0-licensed with no commercial license on file, a legal exposure if the web UI is ever run beyond `0.0.0.0`-bound personal use or the project is distributed closed-source. Additionally, two dependency manifests coexist (`pyproject.toml`/`uv.lock` as the authoritative UV-managed source vs. a stale, loosely-pinned `requirements.txt`) — installing from the latter would not reproduce the audited environment and could reintroduce already-fixed CVEs; the same `requirements.txt` also has `umap-learn`/`hdbscan` commented out, which the `gardener_assign` component report confirms causes a silent, undocumented fallback from the intended UMAP+HDBSCAN clustering to a cruder KMeans heuristic on a fresh install. The core web/data stack (FastAPI, Starlette, Uvicorn, Jinja2, python-multipart, Pydantic, PyTorch/torchvision) is current and past all known CVE fix versions.

## Critical Findings

### Security Risks
- **CVE-2026-45829 (CVSS 10.0)** — unauthenticated RCE in `chromadb`'s FastAPI server component; not exploitable in this codebase's current usage (embedded `PersistentClient` only) but the vulnerable code ships in the installed package.
- **`bleach` end-of-life** — the project's only HTML sanitizer, feeding directly into `markdown.py`'s render pipeline and the web UI's rendered note/MOC/source views, will never receive another security patch.
- **`PyMuPDF` AGPL-3.0 licensing** — no commercial license on file; a compliance risk if the web UI (bound to `0.0.0.0`) is exposed beyond personal use, or the project is distributed closed-source.
- **Unmitigated prompt-injection risk in `connector.py`** — explicitly acknowledged in-code (`connector.py:212-215`) but not yet addressed; source excerpts flow into the LLM prompt for permanent-note generation without injection defenses.
- **Web review endpoint gap** — `review.py`'s `/review/action` web path enforces the auto-approve confidence threshold only client-side, unlike the CLI path; the web's manual `"review"` operation also bypasses `literature_review.auto_approve_min_confidence` entirely, unlike `run_all`'s automated Phase 3.
- **Missing image rendering + no static route for assets** — `markdown.py` strips both standard `![alt](path)` images (allow-list excludes `img`) and Obsidian `![[embed]]` syntax (not CommonMark), and no route serves `90_Assets/` — a compound, user-visible functional gap in the web UI, not a security issue but worth flagging alongside it.

### Technical Debt
- **Zero test coverage on `cli.py`** — no test in the 391-test, 37-file suite imports `zettel.cli`, uses `typer.testing.CliRunner`, or drives it via subprocess, despite it being the sole orchestration entry point for every pipeline command; the `__main__.py` entry point and `new_note`'s Typer wrapper share this gap.
- **No cross-store transaction guarantee** between SQLite and ChromaDB — flagged independently in `review`, `index`, `state`, `purge_source`, and `sync` component reports as a source of potential drift between the two stores on partial failure.
- **Stale `requirements.txt`** diverges from the authoritative `pyproject.toml`/`uv.lock`, risking reintroduction of already-fixed CVEs, and its commented-out `umap-learn`/`hdbscan` silently degrades MOC clustering quality on a fresh install.
- **A confirmed high-risk dead-code bug**: an unconditional early return in `harvester._resolve_content_paging` (harvester.py:1782-1789) makes the content-start heuristic unreachable for every non-interactive harvest path (CLI `--yes`, `run-all`, and the web UI's default harvest job), silently defaulting file page 1 = book page 1 unless `--content-start-file` is passed explicitly — with no test that would catch it.
- **Untested LLM-enrichment and orchestration paths** — `bibliography.py`'s LLM-merge logic (every test fixture disables it), `connector.py`'s core `run_connect`/`_process_candidate` orchestration, and several `extractor.py`/`harvester.py` interactive/heuristic branches have no direct or indirect test coverage.
- **No shared test fixtures** — the 37-file test suite has no `conftest.py`; roughly 15+ near-identical `StateDB`/`tmp_path` fixtures are redeclared per file, and there is no pytest configuration (`pytest.ini` or `[tool.pytest.ini_options]`) anywhere in the project.
- **Dead/inert code confirmed in `cli.py`** — a tautological expression (`skip_paging=skip_paging or True`) makes the `--skip-paging` flag inert in non-interactive harvest; `main.py` and `cuda-test.py` are confirmed unreferenced anywhere in the project outside documentation.
- **Duplicated logic across sibling modules** — `gardener_hub.py` reaches into ~11 private symbols of `gardener.py`; `assets.py` duplicates and reaches into private internals of `llm.py`'s provider-branching logic; the wikilink-matching regex is independently duplicated (with inconsistent strictness) across `markdown.py`, `article.py`, and `sync.py`.
- **Documentation/code drift** — CLAUDE.md states `run-all` is "Not exposed in web," but `web_app.py`'s dispatch table and a tested `web.py` route both support it; `zettel doctor`'s prompt-integrity checklist omits the two `moc_hub_*` prompt files that `gardener_hub.py` actually depends on, and doesn't check `moc_topics.yaml`/`personalities.yaml` despite both being referenced by path from `config.yaml`.

### Single Points of Failure
- **`config.py` and `state.py`** — the two highest-afferent-coupling modules in the codebase (25 and 22 dependents respectively); any breaking change to either has the widest possible blast radius.
- **`cli.py`** — the sole orchestration root with the highest efferent coupling (21 internal module dependencies) and no test coverage of its own to catch orchestration-level regressions.
- **`retrieval.py`'s `Retriever`** — shared by `ask`, `article`, `connector`, and `sync`; its relevance-floor logic has already caused one documented production bug (unconditional BM25 bypass), underscoring how much downstream behavior depends on this single component.
- **`harvester._resolve_content_paging`'s dead branch** — silently affects every non-interactive harvest run (the majority of real-world usage, including `run-all` and the web UI), making page-number attribution wrong by default unless the operator remembers an undocumented workaround flag.
