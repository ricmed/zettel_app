## 1. Executive Summary

`main.py` and `cuda-test.py` are two unrelated, standalone scripts sitting at the project root, outside the `zettel/` package that implements the actual application (the `harvest -> extract -> review -> connect -> garden` pipeline and the FastAPI web UI, per `CLAUDE.md`).

- **`main.py`** (7 lines) is a placeholder generated by the `uv init` / project-scaffolding convention. It defines a `main()` function that prints `"Hello from zettel-app!"` and calls it under `if __name__ == "__main__":`. It contains no business logic, no imports from `zettel/`, and is not referenced anywhere else in the codebase.
- **`cuda-test.py`** (12 lines) is a standalone diagnostic script that imports `torch` and prints whether a CUDA-capable GPU is available, the device name, the installed `torch` version, and the CUDA runtime version bundled with that `torch` build. It is a manual, ad-hoc environment-verification tool, not invoked by any pipeline module, CLI command, test, or deployment script.

**Key findings:**

1. **Neither file is the application's real entry point.** The actual CLI entry point is `zettel/__main__.py` (`python -m zettel`, delegating to `zettel.cli.main`), and the web entry point is `uvicorn zettel.web:app` (used both by `.replit`'s `[deployment]`/`[[workflows.workflow.tasks]]` blocks and by the `CLAUDE.md` build instructions). Neither `main.py` nor `cuda-test.py` appears in `.replit`, in any workflow task, in `requirements.txt`/`pyproject.toml` (`[project.scripts]` is absent — there is no console-script entry point at all), or in any test file.
2. **Both files are dead weight relative to the pipeline**, in the sense that removing them would not break any documented or discovered code path. `main.py` duplicates the naming of the real package entry point (`zettel/__main__.py`) and could mislead a new contributor into running `python main.py` expecting the CLI. `cuda-test.py` duplicates — in a cruder, one-off form — logic that already exists as first-class, tested application code in `zettel/config.py` (`_cuda_available()`, `_gpu_name()`, `get_gpu_info()`, `detect_device()`), which is wired into `zettel doctor` and the CLI startup banner (`zettel/cli.py:229-234`, `zettel/cli.py:1829-1837`).
3. **No test coverage exists for either file**, and none should be expected: `main.py` has no branching logic to test, and `cuda-test.py` has a hardware-dependent conditional (`torch.cuda.is_available()`) whose real counterpart in `zettel/config.py` is exercised indirectly through `zettel doctor` but is also not unit-tested with a mocked GPU/no-GPU path (confirmed by inspection of `tests/` — see Section 11).
4. An earlier architectural analysis of this project (`docs_project/architectural-analyzer/architectural-report-2026-08-30_10-22-26.md`) independently reaches the same conclusion, labeling `main.py` a "Vestigial/dead entry point" (Low risk, developer-confusion impact) and `cuda-test.py` a "Standalone CUDA availability diagnostic script" outside the pipeline (see lines 75-76, 135-136, 228 of that report).

## 2. Data Flow Analysis

Neither script participates in the `harvest -> extract -> review -> connect -> garden` data pipeline, nor in the web request/response cycle. Each is a fully self-contained, single-shot script.

**`main.py` execution flow (when run directly via `python main.py`):**
```
1. Python interpreter loads main.py
2. `if __name__ == "__main__":` guard evaluates True
3. main() is called
4. print("Hello from zettel-app!") writes to stdout
5. Process exits (no return value, no side effects, no I/O beyond stdout)
```

**`cuda-test.py` execution flow (when run directly via `python cuda-test.py`):**
```
1. Python interpreter loads cuda-test.py
2. `import torch` triggers PyTorch's native/CUDA driver initialization
3. torch.cuda.is_available() queries the CUDA runtime/driver for a usable GPU
4a. If True:  print CUDA availability flag + torch.cuda.get_device_name(0) (queries device 0's driver-reported name)
4b. If False: print "CUDA não está disponível."
5. Unconditional: print two blank lines (visual separator)
6. Unconditional: print torch.__version__ and torch.version.cuda (installed package metadata, no device query)
7. Process exits (no return value, no file I/O, no network I/O, no persistence)
```

Both scripts are terminal nodes with no upstream producers and no downstream consumers within the codebase — there is no data flow *into* the rest of the system from either file.

### Business Rule: CUDA Availability Diagnostic Branch (cuda-test.py)

**Overview:**
`cuda-test.py` branches its console output based on whether PyTorch reports a CUDA-capable device as available on the current machine. This is the only conditional logic in either analyzed file.

**Detailed description:**
The script calls `torch.cuda.is_available()` once and evaluates it directly in an `if`/`else` at module scope (cuda-test.py:3,8) rather than storing the result in a variable — meaning the check is executed a second time inside the `if` body via an f-string (`f"CUDA Disponível: {torch.cuda.is_available()}"`, line 4) purely for display purposes; this is a minor inefficiency (two GPU/driver queries instead of one) but has no functional consequence since `torch.cuda.is_available()` is a cheap, idempotent, side-effect-free query after the initial CUDA context probe.

When the branch evaluates True, the script prints the availability flag and the human-readable device name of GPU index 0 via `torch.cuda.get_device_name(0)` (line 5). This hardcodes device index `0`; on a multi-GPU host, GPUs at index 1+ are never queried or reported, which is consistent with the script's stated purpose as a quick single-GPU sanity check (per the inline PT-BR comment on lines 6-7, PyTorch does not directly expose a "CUDA core count," only the device name — this is documented as a known library limitation, not a bug in the script). When the branch evaluates False, the script prints a single PT-BR message, `"CUDA não está disponível."` (line 9), with no further diagnostic detail (no reason code, no distinction between "no NVIDIA driver," "no compatible GPU," or "CUDA-disabled torch build").

This logic exists purely for interactive, human-in-the-loop environment verification (e.g., confirming a GPU passthrough or driver installation succeeded before running the real pipeline) and produces no return value, log entry, exception, or state change consumable by any other part of the system. It is functionally superseded within the actual application by `zettel/config.py`'s `_cuda_available()`, `_gpu_name()`, and `get_gpu_info()` (lines 359-395), which wrap the identical `torch.cuda.is_available()` / `torch.cuda.get_device_name(0)` calls behind `try/except ImportError` guards (so a torch-less environment does not crash) and expose the result through `zettel doctor` and the CLI startup banner rather than a standalone script.

**Rule workflow:**
```
1. Import torch (triggers CUDA driver/runtime detection at import/first-use time)
2. Evaluate torch.cuda.is_available() [1st call, in `if` condition]
3a. IF True:
    3a.1. Re-evaluate torch.cuda.is_available() [2nd call, inside f-string] and print it
    3a.2. Call torch.cuda.get_device_name(0) and print it (device 0 only, no loop over torch.cuda.device_count())
3b. IF False:
    3b.1. Print static "CUDA não está disponível." message
4. Unconditionally print two blank lines
5. Unconditionally print torch.__version__ and torch.version.cuda (static package metadata, independent of steps 1-3)
6. Script terminates (exit code 0 regardless of branch taken; no explicit error handling for torch import failure — an ImportError here would crash the script with a traceback rather than a graceful message)
```

### Business Rule: Placeholder Entry Point (main.py) — no conditional logic

**Overview:**
`main.py` contains a single unconditional statement and no branching, validation, or domain logic of any kind.

**Detailed description:**
The file defines `main()` as a function whose only statement is `print("Hello from zettel-app!")`, then guards a call to `main()` behind the standard `if __name__ == "__main__":` idiom. There is no argument parsing, no environment variable access, no import from the `zettel` package, no configuration loading, and no interaction with `StateDB`, `VectorIndex`, or any vault path. This is the canonical placeholder body generated by Python project scaffolding tools (e.g., `uv init`) and, based on the single-commit git history for this file (`d18a0f0`, "Commit Inicial: versão 0.1.0"), it was never subsequently developed — it has had zero commits since the initial scaffold while the rest of the `zettel/` package grew to the pipeline described in `CLAUDE.md`.

Because it contains no conditional logic, there is no rule workflow to document beyond "always print a static string." Its only practical effect on the project is naming collision/confusion risk with the real entry point `zettel/__main__.py`, which is invoked via `python -m zettel` per the `CLAUDE.md` build instructions — a distinction that is easy for a new contributor to miss given both files are named around "main".

**Rule workflow:**
```
1. Script is executed directly (python main.py)
2. __name__ == "__main__" evaluates True
3. main() is called
4. Static string is printed to stdout
5. Script terminates (exit code 0, no error paths exist)
```
