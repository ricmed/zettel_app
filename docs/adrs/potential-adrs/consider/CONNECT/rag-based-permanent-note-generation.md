# Potential ADR: RAG-Based Permanent Note Generation

**Module**: CONNECT  
**Category**: Architecture / RAG Pattern  
**Priority**: Consider (Score: 75)  
**Date Identified**: 2026-08-30  

---

## What Was Identified

The CONNECT module (Phase 3 of the pipeline) uses a **Retriever-based Reciprocal Rank Fusion (RRF) pattern** to provide contextual evidence when generating permanent (Zettelkasten) notes through Prompt 2. Rather than generating notes in isolation, the connector queries the note graph for relevant existing notes (via hybrid dense+BM25 search) and includes them as structured RAG context, organized by source (embedding seeds vs. graph neighbours). The LLM then uses this context to propose typed connections (`supports`, `contradicts`, `extends`, `depends_on`, `exemplifies`) between the new note and existing ones.

This decision was introduced in July 2026 with the commit "Add hybrid retrieval (BM25+vector) and lightweight GraphRAG" (2026-07-18), and has been stable for over a month. The pattern emphasizes:
- **Separation of concerns**: RAG context assembly is isolated in `_build_rag_context()` with explicit structure (embedding hits vs. graph neighbours)
- **Reuse**: The same `Retriever` composition point used by connector is also used by `ask`, `article`, and `sync` modules, making it a shared infrastructure decision
- **Transparency**: Context includes explicit provenance (hop count, relation types, anchors) so the LLM can distinguish direct retrieval matches from graph-based expansions

---

## Why This Might Deserve an ADR

- **Impact**: All permanent notes generated by the pipeline depend on this retrieval strategy. The quality and diversity of proposed connections directly affects note-graph cohesion and downstream MOC generation.
- **Trade-offs Visible**: The decision to split RAG context into two groups (embedding seeds vs. graph neighbours) reflects a conscious choice to let the LLM weigh different types of evidence differently. An alternative would be to combine all hits into a single flat context.
- **Complexity**: The implementation spans `Retriever` (hybrid search + relevance floor), `graph.py` (BFS expansion), `retrieval.py` (RRF fusion), and `connector.py` (RAG context formatting). Changes to the retrieval strategy ripple across all four modules.
- **Team Knowledge**: Everyone implementing note-generation features or debugging poor connection proposals needs to understand how RAG context is assembled and prioritized.
- **Temporal Context**: Stable for 1+ months, with modifications focused on robustness (e.g., "fix BM25 stopword leak" in 2026-07-18) rather than fundamental strategy changes.

## Questions to Address in ADR (if created)

- Why use hybrid (dense+BM25) search instead of vector-only for note retrieval? (Answer: lexical matches catch jargon/acronyms embeddings miss; documented in retrieval.py docstring)
- Why split RAG context into two sections (embedding vs. graph)? (Answer: to let the LLM distinguish direct matches from typed connections; see `_build_rag_context` comment)
- How does the relevance floor interact with RAG context? (Answer: floor gates hits before they're included in context; documented in retrieval.py lines 148-200)
- What is the cost trade-off between RRF complexity and the benefit of hybrid search? (Answer: RRF is O(n) merge on rank lists; BM25 adds SQLite FTS5 query overhead; no explicit cost analysis in code)
